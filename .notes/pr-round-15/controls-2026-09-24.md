# The two controls the addressing work was waiting on — both pass

Recorded as unmeasured in [pr-round-10/unaddressed-write-finding.md](../pr-round-10/unaddressed-write-finding.md).
Run on the Flipper, app Wipe, 2026-09-24.

## Control 1 — does `gen-2-card` still wipe? YES

`gen-2-card`: **Wipe complete / Cleared 64 blocks. Card claims 64.**

So the TI Tag-it refusal is purely a silicon difference and nothing regressed. The premise the
addressing work rests on holds: unaddressed WRITE BLOCK works on this card. (The TI half of this sentence -- that it is refused there -- was withdrawn 2026-09-24: TI refuses a write with no OPTION flag, addressed or not.)
Had this failed, TI would have been a second problem and the fix a different shape.

## Control 2 — do gen1 cards accept unaddressed WRITE BLOCK for ORDINARY data blocks? YES

`slix-1k-50mm`: **Wipe complete / Cleared 28 blocks. Card claims 28.**

Previously only the backdoor blocks were known to take unaddressed writes, via the gen1 UID
sequence. A gen1 CLONE writes data blocks through the same path, so this was load-bearing and
untested. Twenty-eight of twenty-eight cleared.

## What control 2 also confirmed, without being asked to

**No "UID changed" screen, and the UID did not move.** That is the reach rule predicting a bench
outcome, and it is the first time it has been checked against hardware rather than against the code.

The card claims 28 and goes silent at 28, so A = 28 and claim = 28:

    L = max(A + 7, claim - 1) = max(35, 27) = 35

56 is reached from A >= 49 OR claim >= 57. Neither holds, so the sweep stops at 35, never asks
56/57, and the UID registers are untouched. Blocks 28..35 are the tail-drop, which is why the report
says 28 rather than 36.

Contrast the LRi2K at claim 56: 56 >= 49, so it DOES reach them -- which is the recorded
"Wiped 58/58" reproduction where the UID went to all zeros. The two cards sit on opposite sides of
the same rule and both behave as the closed form says.

## Consequence

Nothing blocks the addressing work. Both premises hold, and the only silicon known to refuse
unaddressed WRITE BLOCK remains TI Tag-it HF-I Plus. (Withdrawn 2026-09-24: it refuses a write with
no OPTION flag, addressed or not, and takes an unaddressed write that carries one.)

## No chip in this project REQUIRES an addressed write — settled 2026-09-24

Asked directly, because it decides whether addressing is a compatibility fix or a safety one. Every
one of the five CARDS is measured taking an UNADDRESSED write. Four of them name a chip; the fifth
cannot, and the row says so rather than borrowing the type line a reader prints for it:

| chip | card | the unaddressed write it took |
|---|---|---|
| TI Tag-it HF-I Plus | `white-coin` | `42 21 08 AABBCCDD` -- with the OPTION flag |
| NXP ICODE SLIX | `slix-1k-50mm` | `02 21 38 00000000` |
| NXP ICODE SLIX-S | `SL2S5302` | the gen1 data-block control below |
| ST LRi2K | `lri2k-keychain` | `02 21 38 03830050` |
| unknown -- see below | `gen-2-card` | control 1 above, a full 64/64 wipe |

**`gen-2-card` has no known silicon, and "EM-Marin" is not it.** That string is the proxmark TYPE of
the expired access credential cloned onto the card in 2026-07, before the project's first
instrumented read -- recorded in `tools/tag-inventory.json` under `carries_cloned_credential`, whose
own note says the UID, TYPE, IC ref, DSFID and geometry there all belong to the credential and
nothing in it describes the card. The card's own measured facts are 64 physical blocks and gen2
magic; its chip has never been captured and now cannot be. Counting it as a fifth chip is the same
error this round corrected in the release notes -- reading a type line decoded from a UID as a
statement about silicon.

So addressing is **not required by any silicon we have**, and it is not a compatibility fix. It is
what #251 filed it as: keeping a write off a second tag in the field. Nothing measured argues against
it either -- all five accept it, four filter on it.

`slix-1k-50mm` is wiped but its UID is intact, so no restore is needed -- which is itself the result.
