## FINDING — Retry after a gen1 opt-in re-runs gen1 with no consent screen

`iso15693_force_gen1` is set true in exactly one place, the opt-in (`gen1_optin.c:93`), and cleared
in exactly one place, the ISO15693 menu (`iso15693.c:63` and `:73`).

Retry on the write-fail screen does `scene_manager_previous_scene`, which returns to
`NfcMagicSceneWrite`, which re-runs the write on enter reading `iso15693_force_gen1` -- still true.
So **any route back into the write scene that does not pass through the menu repeats the destructive
gen1 write without re-consent.**

Noticed at the bench as "the second write no longer gives me the gen1 warning, it just writes".

Why it is worth more than it first looks: Retry does not re-identify the card. Consent was given for
the card that was present. A Retry after CardLost -- the case Retry exists for -- can land on a
DIFFERENT card, and that one gets four blocks written having never been offered the screen.

Not previously recorded anywhere. Sits with the gen1 caveat gate in the addressing work, since both
are about what the gen1 path is entitled to claim and do.

## RAISED WITH HIM, deliberately not fixed here

The protocol menus keep their cursor across a whole new card scan, not just within one. Hit twice at
the bench: write UID, success returns to the main menu, Check Magic Tag, More -- and the cursor is
still on Write UID rather than the menu's first item.

Three things decided it:

- **It is app-wide.** All six protocol menus set scene state on event, read it on enter and never
  clear it. ISO15693 is not the odd one out, so fixing only it would make it one.
- **There is exactly one place it would go.** `magic_info.c` dispatches every protocol menu after a
  scan -- eight `next_scene` calls in one function -- so the fix is about six lines, and it is all
  six menus or none.
- **Index 0 is `Write` in every one of them.** So "reset to the first item" puts every fresh scan's
  cursor on the destructive action, which is precisely what `62b60e2b` was written to stop. His
  rationale is "submenu_reset drops the cursor to index 0, which is Write". The request and his fix
  point opposite ways on the same axis.

Both are coherent -- preserve within a session, reset across sessions -- and the tension does not
kill it. But it is shared app code in a PR about ISO15693, and he has just written the commit that
moved the cursor off Write, so it is his call. Raised in the round-14 reply.
