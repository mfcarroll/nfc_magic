# ISO15693 / NfcV in NFC Magic

NFC Magic reads any ISO15693 tag, and clones, wipes or re-UIDs a magic one. This page is the reference
for how that works: the magic types it knows, what each operation does, what each result screen means,
and what it was tested on. What changed in each release is in the [changelog](CHANGELOG.md).

## Before a wipe

- **A wipe can move a gen1 card's UID.** On gen1 the UID lives at block addresses 56/57, and a wipe
  zeroes every block it reaches. It re-reads the UID afterwards and, if the UID moved, prints the one
  the card now answers to, which can be all zeros: not a valid ISO15693 identity at all. How far the
  sweep reaches depends on both what the card claims and where it stops answering reads, so staying
  short of 56/57 takes a low claim and early silence together. A wipe that clears nothing does not
  re-check the UID, yet on a gen1 card it may still have moved. Tracked in #255.
- **A wipe can destroy a gen3 card.** A gen3 card keeps its UID in blocks 0x10/0x11 and a configuration
  signature in 0x14/0x15, inside any claim, and the wipe does no magic detection, so it zeroes both. Per
  0x6r1an0y, who wrote proxmark's ISO15693 V3 magic support, that **bricks an un-finalized card
  permanently**; the bricking is their report, not tried in testing. The confirm screen, "Wipe?
  (gen1/gen2 only)", warns about it on every wipe, since it cannot tell which card is on the reader.
  Tracked in #255.
- **Keep one tag in the field at a time** — see [Limits](#limits).

## The magic types

The app knows three generations of magic ISO15693 card, told apart by how each changes its UID.
proxmark names them the same way: `hf 15 csetuid` for gen1, with `--v2` for gen2 and `--v3` for gen3.

### gen2

A backdoor command set, through which the UID is written and so is what the card reports about itself:
its block count, block size and IC reference. It is the app's first choice for a clone or a Write UID,
and the only type whose copy reports the same chip as the file.

The advertised block count is a setting, not a capacity. Cloning a 28-block file onto a 64-block card
makes it claim 28 while the blocks above stay readable and writable, which is why a wipe does not trust
the claim, and why a clone reads above the file before it reports (see [Clone](#clone)).

The backdoor is reachable only unaddressed. On all four gen2 cards tested it refuses the addressed
form, while each accepts an addressed ordinary write and ignores one addressed a byte wrong. So another
gen2 card in the field takes these frames too, and nothing in the app can prevent it.

### gen1

No backdoor commands. The UID is written with an ordinary WRITE BLOCK to block addresses 56 and 57,
half of it at each, and takes effect at once: an inventory in the same field session already returns
the new UID. 62/63 are two more registers, which proxmark writes first and this app calls unlock and
commit; what they do is inferred. On all three gen1 chips measured, 56/57 took a write with no unlock
or commit sent before it, writes to 62/63 were refused, and none of the four answers a read.

gen1 has no configuration register, so a gen1 card goes on reporting its own block count and IC
reference whatever it is cloned from. And since 56/57/62/63 are registers, a file's data at those four
addresses cannot be stored on one.

### gen3

The UID is in blocks 0x10/0x11 and a configuration signature, `A5 2B 44 2C` / `21 AE 93 00`, in
0x14/0x15. The card stays rewritable until proxmark's `hf 15 cfinalize` locks it, irreversibly. **The
app does not support gen3.** The gen2 backdoor leaves its UID alone, so a clone or a Write UID stops at
the gen1 opt-in, and accepting that writes 56/57/62/63 as ordinary data: those four blocks of the card
are overwritten, the UID does not move, and the configuration is untouched. See the gen3 warning above
for what a wipe does.

### Not magic

A tag that is not magic leaves its UID unchanged under the gen2 backdoor, so a clone or a Write UID
stops at the gen1 opt-in having written nothing, and backing out leaves the tag as it was.

## What each operation does

A tag that activates as ISO15693 gets its own menu: **Write**, **Wipe**, **Write UID** and **Info**.

### Info

The UID, manufacturer and chip type; what GET SYSTEM INFO reports (block count and size, DSFID, AFI, IC
reference); and every block's data, scrollable, with `*` marking a locked block. The chip decode tells
NXP SLI, SLIX and SLIX2 apart, and their -S and -L variants.

### Clone

**Write** clones a saved `.nfc`: an ISO15693-3 dump, or a SLIX save from the stock NFC app, of which it
writes the ISO15693-3 data and not SLIX-only settings such as passwords or privacy mode.

1. **The UID**, through the gen2 backdoor, which on a gen2 card also sets the file's block count, block
   size and IC reference. It is read back after an RF field power-cycle, and nothing else is written
   until it reads back as the file's, so a card that does not take it is left untouched. That is why a
   clone has no confirm screen.
2. **If the UID did not change**, the card is not gen2, and the app stops at **"Not gen2 magic card"**,
   which says what a gen1 attempt writes and what it costs on a tag that turns out not to be gen1, and
   whether the file's own data at 56/57/62/63 can be carried. **Try gen1** writes those four registers
   first and the data only if that UID takes, so such a tag loses at most those four blocks, and a
   failed attempt names them so they can be restored from a backup.
3. **The AFI and DSFID**, each read back afterwards; a field the copy does not carry makes the clone
   Partial.
4. **Every data block of the file.** The pass is not capped at the card's advertised count, because
   only a write settles whether a block exists; a block that refuses every retry is then read, and one
   that answers a read is not past the card's end. On gen1 the four register addresses are skipped.
5. **A survey above the file.** A clone writes the file's blocks and nothing else, so on a larger card
   everything above them keeps the previous card's data, and a gen2 clone then reprograms the
   advertised count down to the file's, making an ordinary dump look like a clean copy. So the clone
   reads what lies above the file and what the card now reports, and says what it finds.

**A gen1 card that already carries the file's UID** passes the gen2 check, since that check proves
only that the UID matches, and re-cloning the same file is exactly how a card comes to be in that
state. The write that then reaches 56/57 moves the UID, and that identifies the card as gen1: the clone
carries on as a gen1 clone, puts the UID back, and reads it back before reporting. It ends as a clone
onto a card known to be gen1 from the start would.

### Wipe

After the confirm screen, the wipe zeroes every data block the card physically holds, **56/57/62/63
included**: on a gen2 card they are ordinary data, and sparing them would leave real data behind. The
sweep runs past the advertised count until a run of blocks answers neither a write nor a read, and
re-probes a silent run before taking it for the card's top, so a momentary dropout is not mistaken for
the end of the card.

A block counts as cleared only if it takes the zero-write or reads back clear, so an interior dead
stretch — one with a block above it that still answers — is reported rather than written off.
Afterwards the wipe power-cycles the field and re-reads the UID; see the gen1 warning above.

### Write UID

Enter a UID (it starts with E0), confirm, and the app writes it through the gen2 backdoor, offering the
same gen1 opt-in as a clone if the UID does not change. A UID the card already has is refused: a
read-back against the card's own UID passes on any tag, so it would prove nothing.

### How writes reach the card

- **Every write that can carry the card's address does** — the data blocks, the AFI and DSFID, and the
  gen1 sequence — so a second tag in the field is not written by them. That matters to a bystander:
  AFI is what a reader uses to inventory selectively, so a changed AFI can drop another tag out of the
  system that owns it while it still reads fine to anything generic. The gen2 backdoor is the one write
  that cannot be addressed (see [gen2](#gen2)).
- **A card that needs the OPTION flag gets it.** Some silicon refuses a write whose OPTION bit is clear
  and says so with its own error code, which the app acts on. Such a card then owes its acknowledgement
  only after a signal the firmware's ISO15693 API cannot send, so the app reads each block back instead
  of waiting for one. TI Tag-it HF-I Plus is such a card.

### While a write runs

The popup counts "Writing X / N" or "Wiping X / N". **Back is ignored** from the moment a card is found
until the write reports: it could not stop a write in any case, and leaving a clone between its UID and
its data could strand the card with a new UID and none of the file. A time limit bounds each pass, so
the screen is never held for the whole block range.

**Hold the card still.** Lifting it makes every remaining block fail, which looks exactly like the card
running out of capacity, so before calling anything a capacity edge the app checks the card is still
there, and a lifted card is reported as removed.

## Reading the result

A clone or a Write UID that has nothing to add ends on **"Success!"**. Everything else gets a result
screen, whose summary carries the counts and the most significant caveat; **Details**, where offered,
lists every block and note behind it.

| Screen | What happened |
|---|---|
| **Clone finished** | Everything that fits was written and nothing was lost, with a note: data from before the clone still above the file; a card answering reads past the count it reports; a block count or IC reference other than the file's that the card goes on reporting, as a gen1 card does; or, on gen1, the four register addresses the file reached with nothing in them. Or the file was larger than the card and its blocks past the card's end were empty: "Holds X/Y blocks." |
| **Clone partial** | Part of the file did not make it, with the reason that matters most: the time limit ("Timed out at block N", with Retry), a card smaller than the file ("Card too small"), gen1 registers where the file held data ("gen1: 56/57/62/63 differ"), or an AFI or DSFID the card did not take ("AFI/DSFID not set"). |
| **Clone failed** | The UID was written but no data block took: the card has the UID only. |
| **Nothing to clone** | The file has no data blocks. Nothing was written. |
| **Wipe complete** | "Cleared N blocks. Card claims M." Both figures and no verdict, since the claim is a setting. "UID not re-checked" when the card did not answer the check afterwards. |
| **Wipe stopped** | The time limit ended the sweep, with Retry. Details says where it stopped against what the card claims. |
| **Wipe partial** | Some blocks would not clear, and Details names them. |
| **Wipe failed** | No block accepted the zero-write. |
| **UID changed** | The wipe moved the UID, in practice on a gen1 card whose 56/57 it reached. The screen prints the UID the card answers to now. |
| **Unexpected UID** | The UID moved, but to neither the original nor the one asked for. That proves the card is magic, and the screen prints the UID it answers to. |
| **gen1 failed** | The gen1 UID did not take, so this is not a gen1 card, and 56/57/62/63 may have been overwritten. |
| **UID unchanged** | Write UID was given the UID the card already has. Nothing was written. |
| **Write failed** | The card left before the write finished, with Retry; or it left during a gen1 attempt, after which 56/57/62/63 may differ. Where offered, Details says the UID was not re-checked. |

Retry after a time limit may get further, but the limit is a time budget, not a position: a card that
stops at the same block again is too slow to finish in one pass rather than refusing.

## Limits

- **One tag in the field at a time.** Besides the gen2 frames, the app's reads and inventories are
  unaddressed, and the UID re-reads in particular — after a wipe, and after a clone that reached blocks
  56/57 — can answer with a bystander's UID rather than the card's. Addressing cannot fix that: those
  reads exist to find out whether the UID changed, so they cannot be aimed at a UID already in doubt. A
  badge holder or a wallet is enough to break this. Tracked as #251.
- **A block already dead when the card was presented** cannot be told apart from memory the card never
  had: the read taken at activation stops at the first block that does not answer, so nothing above
  that point can be proven either way, and a wipe drops such a stretch rather than reporting it.
- **A card whose address space aliases** answers a read at all 256 block addresses, so the clone's
  survey would take a 128-cell card for a 256-block one. No gen1 or gen2 card tested does this; two
  tested tags that the app does not support do.

## Tested on

- **The addressing**, on seven cards over four identified chips — TI Tag-it HF-I Plus (identified by
  its behaviour, not its UID), NXP ICODE SLIX and SLIX-S, and ST LRi2K — plus two whose own silicon was
  never captured. Every one accepts an addressed WRITE BLOCK, and on every one a write carrying a UID one
  byte wrong was read back afterwards, against a block holding something else, and had changed nothing:
  the address is filtered, not merely unanswered.
- **gen1**, across three chips: ST LRi2K (56 blocks), NXP SLIX (28) and NXP SLIX-S (40). On every one
  the four-frame UID sequence sets the UID, it reads back, and the original restores byte-identically.
  The wipe hazard above was reproduced on the LRi2K, the one card tested whose sweep reaches 56/57.
- **gen2**, end to end: byte-identical clones across 28, 56, 64 and 70-block geometries, the wipe, and
  the over-capacity reporting. The backdoor's refusal of addressed frames was measured on four cards.
- **gen3**, on one genuine un-finalized card: a clone and a Write UID land on the gen1 opt-in as
  described above, the configuration signature is untouched, and the card restored byte-identically.
  The brick was deliberately not tried.
